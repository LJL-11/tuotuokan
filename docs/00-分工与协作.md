# 分工与协作

> 分工依据：`软件创新大赛2026/项目方向摘要.md` 第七节。职责边界以实际为准，鼓励交叉补位。
> 仓库内日常一律用代号 A/B/C。`.github/CODEOWNERS` 顶部的姓名仅为私有仓库内对齐分工的临时占位，
> **不属于提交材料，提交/演示前必须清理**（见 `04-参赛合规.md`）。

## 一、角色与目录 ownership

| 代号 | 职责 | 主要负责目录 | 次要 / 需协作 | 第一个可认领任务 |
|---|---|---|---|---|
| **队长**（产品统筹 + 前端 / 可视化） | 沙盒 UI、参数控件、图表与整体交互、文档与节奏 | `src/viz/`、`src/ui/`、`assets/`、`index.html`、`docs/` | `contracts/`（守门）、`src/learning/graph.js` | #I1 四视图路由接入 |
| **队员 A**（算法 / ML） | 概念→参数化模型映射、AI 生成沙盒、多模态概念识别 | `src/model/` | `contracts/template.schema.json` | #I4 接 LLM 产出 TemplateSpec |
| **队员 B**（游戏 / 模拟引擎） | 沙盒运行骨架 + 前端交互 | `src/core/` | `src/model/dsl.js`（编译器）、`tools/` | #I7 引擎性能与插件化 |
| **队员 C**（后端 / 多设备 / 工程） | 账号系统、跨设备同步、工程化与部署、文档 | `services/api/`、`src/learning/data.js`、`.github/` | `src/learning/graph.js`（跨设备掌握度） | #I10 REST 适配器与匿名同步 |
| 指导老师 | 方向把关 | — | — | 不参与仓库日常提交 |

`contracts/` 是共管区：**任何人都可以提修改，但必须队长 + 全部受影响方 review 通过**。

## 二、为什么会这样切

- 目录边界 = 契约边界。A 只往 `src/model/` 产数据，B 只往 `src/core/` 提供运行时，队长只消费 `ComputeResult` 画图，C 只替换数据适配器。**改自己的目录不需要等别人**。
- 现有 v0 原型代码已按 owner 归位到这些目录，`index.html` 仍双击可运行，等于给每个人留了一个能直接调试的真实环境。
- 已经写好但**尚未接入 UI** 的模块（`expr.js`、`dsl.js`、`data.js`、`graph.js`、`views.js` 骨架、`generator.js` 骨架）就是本次要协作完成的"未完成工作"，逐条拆在 `02-路线图与任务看板.md`。

## 三、分支与提交

```
main            ← 永远可演示、CI 全绿；只允许 PR 合并，不直接 push
└── feat/<代号>-<短名>      例：feat/a-llm-generator
└── fix/<代号>-<短名>
└── docs/<短名>
```

- 从 `main` 切分支，一个分支只做一件事，生命周期尽量短。
- commit 用 `类型(范围): 一句话`，类型取 `feat / fix / docs / refactor / test / chore`，范围用目录名，例如：
  `feat(model): 接入 LLM 模板生成与本地降级`
- **提交前**本地跑 `npm test` 和 `npm run check:anon`。
- PR 必须关联 Issue、填模板自检清单；涉及 `contracts/` 的 PR 需要队长 + 受影响方 approve。
- 合并策略用 **Squash merge**，保持 `main` 历史干净。

### 铁律：先 PR，再由队长合并

| 角色 | 允许 | 禁止 |
|---|---|---|
| 队员 A / B / C | 从 `main` 切自己的分支、push 到自己的分支、提 PR、参与 review | **直接 push `main`**、**点 Merge 合并自己的或他人的 PR**、绕过检查 |
| 队长 | approve / 驳回 PR、执行 Squash merge、维护分支保护规则 | 无（但同样走 PR，不在 `main` 上直接提交） |

- 每个 PR 的准入条件：关联 Issue + CI 全绿 + 自检清单填完 + **队长 approve**。
- `contracts/` 的 PR 额外需要全部受影响方 approve。
- `main` 禁止 force push、禁止绕过检查。这些由 GitHub 分支保护强制执行——
  **没开启保护前只是"靠自觉"**，队长必做步骤见第五节。

## 四、协作节奏（建议）

1. 每周一次短同步：只过「契约有没有要改」「谁被谁卡住」，不汇报流水账。
2. 遇到需要改契约 → 先开 Issue 写清影响面，讨论完再动代码，别在 PR 里临时改字段。
3. 任何"我这边先硬编码一下"都要在 PR 描述里显式标注并建偿还 Issue。
4. 复赛要用的真实试用数据由 `TTK.data.exportAll()` 统一导出，格式见契约，**不要各自造表**。

## 五、队长必做：把「先 PR 再合并」锁死

> **CODEOWNERS 只负责自动加 reviewer，它不阻止任何人直接 push `main`。**
> 要真正控制合并权，必须开分支保护。仓库已建好并推送，接下来只需在 GitHub 网页操作。

**Settings → Branches → Add branch ruleset（或 classic protection rule），Branch name pattern 填 `main`：**

| 勾选项 | 作用 |
|---|---|
| ☑ Require a pull request before merging | 禁止直接 push `main`，只能走 PR |
| ☑ Require approvals：**1** + Dismiss stale approvals on new commits | 必须有人批准；新提交会作废旧批准 |
| ☑ Require review from Code Owners | CODEOWNERS 填好账号后启用，自动把队长加为 reviewer |
| ☑ Require status checks to pass → 勾 `CI` | `npm test` + 匿名扫描不过就不给合 |
| ☑ Do not allow bypassing the above settings | 管理员也不能绕，铁律才成立 |
| ☑ Restrict who can push to matching branches → 只加队长 | 从权限层堵住直接 push |
| ☐ Allow force pushes / deletions：**不勾** | 保护 git 历史 |

**然后依次完成：**

1. Settings → Collaborators → Add people 邀请三名成员，权限给 **Write** 即可，
   **不要给 Admin / Maintain**（否则能改保护规则）。私有仓库不邀请他们 clone 不到。
2. 拿到四人的 GitHub 账号后，替换 `.github/CODEOWNERS` 里的姓名占位与 `@OWNER_*`，
   删除规则行行首 `# `，CODEOWNERS 才会生效（中文姓名不是合法 owner）。
3. 在 Issues 里按 `02-路线图与任务看板.md` 建 I1–I14，贴 owner 标签，**先排 #I13 与 #I1**。
4. 把本节的分支保护截图发群里，让所有人确认规则已生效。
