> 分工依据：`软件创新大赛2026/项目方向摘要.md` 第七节。职责边界以实际为准，鼓励交叉补位。
> 队内分工直接用姓名标注；`owner:a` 等 Issue 标签与 `feat/a-xxx` 分支前缀沿用字母代号（对照见第三节）。
> 姓名仅限私有仓库内部，对外提交 / 演示 / 公开前按 `04-参赛合规.md` 全仓清理。

## 二、为什么会这样切

- 目录边界 = 契约边界。姜雅文只往 `src/model/` 产数据，曹蕾只往 `src/core/` 提供运行时，付嘉一只消费 `ComputeResult` 画图，秦庆泽只替换数据适配器。**改自己的目录不需要等别人**。
- 现有 v0 原型代码已按 owner 归位到这些目录，`index.html` 仍双击可运行，等于给每个人留了一个能直接调试的真实环境。
- 已经写好但**尚未接入 UI** 的模块（`expr.js`、`dsl.js`、`data.js`、`graph.js`、`views.js` 骨架、`generator.js` 骨架）就是本次要协作完成的"未完成工作"，逐条拆在 `02-路线图与任务看板.md`。

## 三、分支与提交

**不设审批门禁**：可以直接 push `main`，也可以开分支提 PR、互相合并，按方便来；不需要 approve，也没有指定合并人。

```
main                           ← 保持可演示、CI 全绿；可直接 push，也可走 PR
└── feat/<代号>-<短名>          例：feat/a-llm-generator（开分支是可选做法）
└── fix/<代号>-<短名>
└── docs/<短名>
```

> 分支 / 标签里的字母代号：`lead` = 付嘉一，`a` = 姜雅文，`b` = 曹蕾，`c` = 秦庆泽。
> 这些是技术标识，保持英文，不写成中文。

- 建议一个分支只做一件事、生命周期尽量短，改完尽快合回，避免多人长时间改同一文件。
- commit 用 `类型(范围): 一句话`，类型取 `feat / fix / docs / refactor / test / chore`，范围用目录名，例如：
  `feat(model): 接入 LLM 模板生成与本地降级`
- **提交前**本地跑 `npm test` 和 `npm run check:anon`（或 `npm run check` 一次跑完）。
- CI 在 push 与 PR 时自动跑 `npm test` + 匿名扫描，红了及时修。
- 改 `contracts/` 字段前先在群里说一声，避免别人在自己的分支里发现字段变了。

## 四、协作节奏（建议）

1. 每周一次短同步：只过「契约有没有要改」「谁被谁卡住」，不汇报流水账。
2. 遇到需要改契约 → 先开 Issue 写清影响面，讨论完再动代码，别在提交里临时改字段。
3. 任何"我这边先硬编码一下"都要显式标注并建偿还 Issue。
4. 复赛要用的真实试用数据由 `TTK.data.exportAll()` 统一导出，格式见契约，**不要各自造表**。
